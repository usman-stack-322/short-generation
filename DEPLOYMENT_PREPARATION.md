# Local operation and deployment preparation

Run `./start-backend.ps1` and `./start-frontend.ps1` in two PowerShell terminals from the project. Both must remain open. These scripts force uploads and daily scheduling off for supervised operation. Open http://127.0.0.1:5173; backend http://127.0.0.1:8000/docs. Port 5212 and older acceptance ports are temporary test URLs, not the normal application.

Generation runs in the API process, serialized locally for narration and FFmpeg. There is no separate worker command. Use one API process and one Uvicorn worker. Restart recovery marks interrupted jobs failed while preserving committed artifacts. Open the job and use Retry failed step. The daily schedule slot remains claimed, so a scheduler tick does not create a replacement job. A media retry preserves unchanged script and narration checkpoints.

Back up `backend/ai_shorts.db`, `generated/`, `backend/.session_secret` and the configured token encryption key together. Keep credentials outside source control. Do not replace the normal database with acceptance databases in generated subdirectories.

The Dockerfiles and compose file are preparation only; no hosting resources have been created. Copy backend/.env.example to a private deployment env file, provide existing provider credentials and a stable APP_SECRET_KEY and TOKEN_ENCRYPTION_KEY, then review every setting. Never copy an existing database into a fresh deployment without a backup and migration rehearsal. Container local narration needs installed matching voices; validate narration independently on the target OS before real use. Linux container behavior has not been tested here.

Before unattended use: provide durable database and media volumes, database backups, a single scheduler leader, durable background task delivery with worker leases and heartbeat recovery, bounded provider retries/budgets, monitoring and alerts, and migration/restore verification. The current in-process worker is suitable for supervised local sessions; it is not a resilient distributed worker. Multiple API workers would each run startup recovery and must not be enabled.

Before a later private YouTube test: obtain explicit authorization identifying one connected channel and one approved content revision; configure OAuth callback and encrypted token storage; verify ownership, credits, narration and source dates; confirm private privacy status and upload quota. In an isolated controlled window, enable uploads for that authorized test channel only, approve the current revision, submit once, record the returned YouTube ID and reconcile any uncertain result in YouTube Studio before retrying. Disable uploads immediately afterward. Do not use a schedule or public/unlisted privacy. No real upload was authorized or performed during this implementation.

Test status (31 October 2026): all previously failing backend tests were reconciled with the current per-member channel access and MEMBER-only role rules and pass when run per file in batches; see RELEASE_TEST_FAILURES.md. Run backend tests in batches of a few files (for example `pytest tests/test_api.py tests/test_safety.py -q -p no:cacheprovider`) rather than the whole directory at once, which times out in a constrained terminal.
